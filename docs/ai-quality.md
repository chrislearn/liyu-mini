# 真实 AI 质量评测

`verification/ai-quality-cases.json` 固定16个虚构场景。覆盖35元咖啡的中英文和重复请求、34.99元边界、软品牌搜索回退、第一页之外的商品、配送限制、连续修改条件、成分/品牌/未知种类无法核验、乔迁偏好、引文提示注入、全目录缺货和下架。

每个场景单独检查条件解释、实际HTTP查询、目录计数、推荐商品编号、预算、库存、配送、精确/备选标记及越权声称。测试的通过判定来自独立Python检查，不能让模型自己判自己的结果。备选推荐最近预算优先、软偏好是否体现另记质量观察；推荐理由需人工阅读核查，包括金额单位错误、把软偏好当硬限制、将“实用”误读成“实物”等语义问题。不能以查询失败、限流或格式失败冒充无匹配。

连续修改场景模拟用户在同一熟人页面修改预算和完整偏好后重新生成，不声称提供自动理解省略条件的聊天记忆。模型通过应用控制的查询循环决定关键词与分页，不把预选推荐注入模型；模型调用使用宿主已有配置，不读取密钥。16秒最小请求间隔用于遵守宿主速率限制。真实调用次数、错误和未完成场景都保留。

## 运行步骤

1. 核验小程序与配套服务端源码版本，在受自己控制的本地PostgreSQL创建新的 `liyu_ai_quality_<唯一编号>` 库，用服务端初始化迁移。只在该库应用 `verification/ai-quality-seed.sql`。记录服务端提交、二进制摘要及数据库配置。禁止使用业务数据库。
2. 编译标准Hub和官方开发用签名测试安装器。测试安装器按 OctoSense 的 `connected_support` 生成仅驻留内存的临时签名密钥、校验安装和启动；这不是公开发布或商店安装，也不得修改生产信任目录。测试依赖这些工具，请自行把下面路径替换为实际路径。
3. 准备、盖章并安装测试夹具到全新目录：

```sh
python3 scripts/real-ai-quality.py prepare --output <独立证据目录> --hub <hub二进制>
<开发测试安装器> <独立证据目录>/live-apps <独立证据目录>/live-bundle > <独立证据目录>/live-receipt.json
```

4. 将测试服务器绑定回环地址，在两个终端分别运行：

```sh
python3 scripts/real-ai-quality.py bridge --output <独立证据目录> --server http://127.0.0.1:<本次端口> --database liyu_ai_quality_<唯一编号> --pg-port <本地PG端口>
python3 scripts/real-ai-quality.py host --output <独立证据目录> --host <官方OctoSense二进制> --home <已配置模型的宿主目录>
```

桥接器仅执行实际本地 `catalog/search-options` 与 `catalog/search` GET，不代为登录、下单、支付或日历写入。它每个场景开始时在专用测试库调整在售/库存状态，随后模型自行查询。应用认证状态及熟人资料为明确的虚构夹具；文件桥替代原生后端认证传输，因此不证明真实账号隔离或完整GUI。

5. `assessment.json` 随每个场景更新。完整结果在 `live-apps/liyu-mini/results.json`，实际HTTP记录在 `http-trace.json`；原始模型请求/响应包含每次输入及输出。用 `assess` 可重新判定：

```sh
python3 scripts/real-ai-quality.py assess --output <独立证据目录>
```

6. 失败修复后在新的输出目录重跑；`prepare --ids <逗号分隔场景编号>` 可定向复测。不要覆盖首次失败、合并重复请求后伪称全次成功，或无限重试到满意结果。结束后仅停止本次测试宿主和服务器，删除本次专用数据库；保留脱敏证据。

## 证据边界

生成的 `source.json` 固定生产脚本摘要和提取函数列表；测试仅将 `host.request` 转接为带速率间隔的真实宿主调用，未替换模型响应。每次新源码、模型配置或目录变化都需要新的证据。历史真实模型结果、合成回归、系统日历、正式安装、公网双账号是不同验收范围。

通过16个固定场景不保证所有自然语言表达正确。种类、库存、价格、配送可用结构化字段校验；成分、型号、材质或品牌等未支持的硬条件只能明确标记无法核验，不能保证满足。全目录零结果证明只适用于当次查询的可执行过滤。扩展此矩阵时应加入实际发现的失败样本，并同时保留安全守卫与推荐质量检查。

金额理由守卫会把含数字金额、货币符号或常见中文金额的模型理由替换为由实际商品整数分生成的说明；普通个性化理由保留。规划提示与结构化字段说明明确区分硬要求、软偏好及配送方式。不能因此宣称任意自然语言解释都正确。

最终字面守卫合并“不要/排除”后明确列出的已知中文种类，不把引文当指令，不推断“咖啡味香薰”等复杂表达。未知或英文语义仍由模型解释；冲突停止，不静默放宽。`prepare --planner-only` 只执行一次真实规划并检查应用锁定条件，不执行新推荐，结果单独标明范围。各阶段失败和完整/规划检查不能混算为同一版完整全绿矩阵。
